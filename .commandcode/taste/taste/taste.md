# Taste
- Wants commit messages and signatures kept free of any AI/coding-agent traces (no `Co-Authored-By`/`Signed-off-by` agent trailers, no mentions of Claude, Command Code, OpenAI, etc.); commits should be attributed solely to them (e.g., "Mohammad Samin-Al-Wasee"). Confidence: 0.9
- Accepts rewriting history and force-pushing to scrub commit messages, as long as file content stays byte-identical and authorship is preserved. Confidence: 0.7
- Prefers tool-generated state directories (e.g., `.commandcode/`) added to `.gitignore` so they can't be committed accidentally, rather than left as untracked clutter — but wants agent skills under them (e.g., `.commandcode/skills/`) to stay tracked/committed so they travel with the repo (e.g., ignore `.commandcode/*` with a `!.commandcode/skills/` negation). Confidence: 0.6
- Wants shared, project-level agent/tool config checked in so it travels with the repo (e.g., committing `.commandcode/settings.json`, including permission allowlists like `Shell(git:*)`), while machine-local overrides (`settings.local.json`) stay git-ignored. Confidence: 0.6
- Wants agent capabilities (e.g., skills) installed scoped narrowly — for Command Code only and at the project level, not globally and not shared with other tools. Confidence: 0.6
- Prefers agent behavior rulesets to be active automatically every session (e.g., wired via a `SessionStart` hook injecting them into the first turn) rather than left as opt-in skills that must be manually invoked. Confidence: 0.6
- YAGNI-first, minimal-scope delivery: wants the smallest slice that delivers value shipped in front of real users first, then expanded — explicitly rejects "build everything first, then find users," gold-plating, and speculative features "for future use". Confidence: 0.8
- Wants work decomposed into small, independently shippable, individually-reviewed slices rather than one giant change. Confidence: 0.7
- Prefers a read-only recon + written, reviewable plan before implementation, with the decisions that "change everything" surfaced and answered up front, and an explicit stop for approval before any code is written. Confidence: 0.6
- Wants to move into implementation once a slice is authorized rather than spending further cycles expanding plans/roadmap docs — favors shipping momentum over more upfront meta-work. Confidence: 0.5
- Wants docs and ADRs to ship in the same change as the code (documentation/decisions land before or with implementation), following the repo's existing ADR/docs standards. Confidence: 0.6
- Keeps a strict separation of concerns: the deterministic core stays pure/headless and free of users, DB, HTTP, and framework concerns; the application layer orchestrates around it. Explicitly rejects duplicating core logic in the frontend/API or making the database the engine. Confidence: 0.7
- Favors implementing with the standard library over adding a third-party dependency when the need is modest — approved building the OAuth 2.0 Authorization Code + PKCE flow on Go's stdlib (`net/http`, `crypto/*`) instead of `golang.org/x/oauth2`, keeping the dependency footprint at zero. Confidence: 0.5
- Prefers PostgreSQL (a production-appropriate RDBMS) for application data, while keeping user/persistence data out of the pure simulation core. Confidence: 0.5
- Holds a firm quality bar: existing gates must keep passing (gofmt, go vet, Go tests, ESLint, tsc, Vitest, Playwright, secret scanning, CI) and new work adds tests rather than relaxing standards. Confidence: 0.6
- Expects authorization and data isolation to be enforced and tested once users exist — one user must not be able to access another's sandbox, submissions, progress, or profile. Confidence: 0.5
- Develops inside a dev container and wants local dependencies (e.g., Postgres) provisioned as services in the devcontainer's docker-compose so the whole environment comes up reproducibly in one command. Confidence: 0.7
- Wants an `.env.example` template documenting required environment variables (with git ignoring the real `.env`), so setup works both inside and outside the devcontainer. Confidence: 0.7
- Applies the "one unit of work per commit" rule at commit granularity: a mixed working tree should be sliced into separate self-contained commits (e.g., `[feat]` for the feature work, `[chore]` for an incidental cleanup) rather than one catch-all commit, even when that means splitting shared doc hunks and temporarily trimming edits so each commit stands alone and is reviewable. Confidence: 0.7
- When agent/tooling state changes are sitting in the working tree (e.g., `.commandcode/settings.json` permission allowlists, taste/learning files), wants them committed as their own separate `[chore]` commit rather than reverted or discarded — and accepts leaving session-specific noise (e.g., one-off command allowlist entries) in rather than cleaning it. Confidence: 0.6
- Prefers feature work committed on a dedicated feature branch (e.g., `feat/phase-13.1a-application-store`) rather than landing directly on `main`, and expects the target branch/scope to be confirmed before committing. Confidence: 0.5
- Commit messages follow the repo's existing convention: a bracketed type prefix subject (`[feat]`, `[chore]`) with a concise summary and a short bullet body of what changed. Confidence: 0.5
