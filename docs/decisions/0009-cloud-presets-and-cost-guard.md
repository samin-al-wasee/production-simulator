# ADR-0009: Terraform cloud presets with a plan-time cost guard (Phase 6)

**Status:** superseded by [ADR-0014](0014-sandbox-only-platform.md) (was accepted; the code it describes is on the `archive/live-lab` branch)
**Date:** 2026-09-28

## Context

Phase 6 adds cloud presets for AWS and GCP, managed-service variants of components, and cost-guard rules for experiments. Cloud resources cost real money and outlive a session, so the presets must be safe by construction, declared as code, optional per component, and must never be applied automatically (AGENTS.md §13). The lab stays local-first and cloud agnostic (principles 6 and 7).

## Decision

1. **Two independent root modules**, `environments/cloud/terraform/presets/aws` and `.../gcp`, each with pinned provider versions, raw provider resources only (no third-party registry modules), and its own lock file. Presets are opt-in layers; nothing in the local or Kubernetes environments depends on them.
2. **Composable by variable:** the cluster is the core (EKS / GKE); the managed database (RDS / Cloud SQL), cache (ElastiCache / Memorystore), and queue with a dead-letter target (SQS / Pub/Sub) are individually switchable with `enable_*` variables. The queue variants reproduce the local RabbitMQ topology (delivery limit → DLQ).
3. **Safe defaults enforced in Terraform:** variable validation restricts instance classes to a small allowlist, node counts to 1–3, experiment lifetime to 72 hours, and budgets to ≤ $500; workers default to Spot; there is no NAT gateway; databases are private; the AWS database password is generated by RDS into Secrets Manager and the GCP database uses IAM authentication, so no credential is stored in variables or git; provider default tags/labels carry `forgelab-experiment`, `forgelab-owner`, `forgelab-ttl-hours` on every resource; AWS Budgets and (when a billing account is given) a GCP budget alert at spend thresholds.
4. **Plan-time cost guard in the Go core:** `core/internal/costguard` and `forgelab costguard check` evaluate `terraform show -json` output against `environments/cloud/cost-guard.yaml`: estimated monthly ceiling, denied resource types (NAT gateways, MSK, Aurora clusters, …), required tags, maximum TTL, and unpriced resources (a violation by default). Prices live in the rules file and are estimates that the user maintains; the guard is pure and needs no cloud access.
5. **Never apply automatically.** `scripts/cloud-validate.sh` (`make cloud-validate`) needs no credentials and creates nothing. `scripts/cloud-plan.sh` (`make cloud-plan PRESET=…`) plans and runs the guard, then stops; there is no apply target anywhere in the repository.
6. A unit test keeps the price table and the presets from drifting apart: the repository's rules must accept default-plan fixtures for both presets.

## Consequences

### Positive

- A mistaken plan (too many nodes, an expensive service, missing tags) is rejected before any spend.
- Presets can be used piecemeal and destroyed by TTL because every resource is tagged.
- Validation runs offline in CI-like conditions.

### Negative / Trade-offs

- Cost figures are approximations from a hand-maintained table and exclude storage and data transfer; the cloud budget alerts remain the source of truth for real spend.
- Nodes run in public subnets (no NAT) to avoid NAT cost; this is acceptable for a lab but not a production network design.
- The presets were validated with `terraform validate` and unit tests only; they have not been applied to a real account by this project.
- Default fixtures approximate plan output; real plans may include attributes the guard does not model, which surface as unpriced-resource violations until added to the rules.

## Alternatives Considered

- **Registry modules (terraform-aws-modules, GKE modules)** — faster to write but add third-party dependencies (AGENTS.md §13) and hide the mechanics.
- **Infracost / OPA / Sentinel for cost policy** — good tools, but adding external services or paid engines for a lab; a small in-core guard covers the needed rules and is testable.
- **A single multi-cloud root module** — rejected: it would force one provider's credentials on users of the other.
- **Apply targets in the Makefile** — rejected outright; applying must remain a deliberate human step.
